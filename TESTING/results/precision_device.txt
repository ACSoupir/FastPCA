Precision x device sweep -- torch_irlba (PyTorch port of irlba's algorithm)
================================================================================
Machine: Apple silicon, macOS.  torch 2.9.0 (BLAS_INFO=accelerate), MPS available.
All runs: memguard.py --cap-gb 20 (SIGKILL above 20 GB tree RSS) wrapped in
/usr/bin/time -l; k = 10 (--nv=10), work = k+7, tol = svtol = 1e-5,
--threads=1 (matmul is single-core through Accelerate/AMX either way),
identical start vector (--seed=42).  Reference for the error columns:
irlba::irlba C fast path on the same centred matrix.

Platform constraints found by TESTING/device_dtype_probe.py
--------------------------------------------------------------------------------
* MPS refuses float64 outright:
    TypeError: Cannot convert a MPS Tensor to float64 dtype as the MPS framework
    doesn't support float64. Please use float32 instead.
  -> an fp64 + GPU request is served on the CPU and reported as
     device_status = "mps-fp64-downgrade"; dtype is never silently changed.
* No native MPS linalg.qr / svdvals / eigh in torch 2.9; plain linalg.svd
  silently falls back to the CPU with a warning per call, so irlba_torch.py
  moves the work x work matrix to the host explicitly.
* The empty-subspace projection in orthog() (j == 0) tripped an MPS internal
  assert ("Placeholder tensor is empty!") until it short-circuits on an empty X.
* fp64 3072-square GEMM: ~320 GFLOPS, cpu/wall = 1.00x at threads=1 and 4
  (single AMX core).  fp32: ~1100 GFLOPS on the same single core.
* MPS does not show up in ru_maxrss: RSS stayed at 3.31 GB while the fp32
  matrix (779 MB) lived on the GPU, so irlba_torch.py also checks
  torch.mps.driver_allocated_memory() each repeat and aborts above --max-gb.
